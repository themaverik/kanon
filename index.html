Kanōn

A ticket-driven, verifier-backed engineering standard for AI coding agents. One canonical source, generated dialects for every editor. Built lean: ~1.4–2.5K tokens fixed per session, not counting MCP tool schemas.

Discipline, as Kanōn uses the word: a named set of rules, roles and checks that the agent follows the same way on every task. Hooks and verifiers enforce it, so nothing depends on the model remembering.

Lean by measurement, strict by default

Most agent standards grow by adding text. Kanōn shrinks by measuring: every rule earns its tokens, every check runs as code, and every pattern points to where it came from. The numbers below come from this repo's files and a year of the author's own Claude Code transcripts.

  • 4.2 KB

    CLAUDE.md template, down from 7.9 KB

    Distilled from the best public packs

    Benchmarked line by line against addyosmani/agent-skills, mattpocock/skills and obra/superpowers, keeping what works and pointing to them for what they do better. Adam Bien's airails ships vendored for Java. The CLAUDE.md template is written so every line earns its place.

  • 190K

    Max 5x compaction target, 205K ceiling, from a 60K floor

    Model routing and compaction that fit your plan

    Subagents run on Sonnet by default, Opus needs approval, and Fable is held to one bounded task per session. cache-keeper reads your plan (Pro, Max, Team or API) and compacts at your real context floor plus working room, capped per plan. Past that target heavy work compacts and a short query holds inside a grace buffer.

  • 3

    opt-in mods, drawn outside the context

    Session mods above the prompt

    See cache time left, context size, 5-hour and weekly use, and session cost on every turn. Hand off and clear in one key. Get asked before editing a file another session just changed.

  • 1.4–2.5K

    tokens fixed per session

    Load only what the repo uses

    Enable core plus your stack. A frontend repo never sees Quarkus text, and airails and the utility skills stay opt-in. Eight tech stack recipes cover Quarkus, Spring Boot, Kotlin, NestJS, Next.js, plain TypeScript and Rust.

  • 1.05K

    tokens in the audited CLAUDE.md template

    Prompts checked for drift

    The CLAUDE.md template, agents, skills and rules are audited with /claude-api prompt-audit against the current Claude models, so instructions written for older models get caught and removed.

  • 6

    hook checks, with 17 bats tests in CI

    Safety gates that run as code

    Hooks block unticketed commits, committed session notes, container and database changes by agents, and dependency-cooldown bypasses. Nothing depends on the model remembering a rule.

  • Mutants

    surviving mutants are the evidence, not an 80% coverage target

    Verifiers, not opinions

    Reviewers are read-only and quote ArchUnit, dependency-cruiser, clippy and cargo-deny output. Tests prove themselves with mutation testing (PIT, Stryker, cargo-mutants), not a coverage percent.

  • 370

    citations across 53 files

    Industry standards, with sources

    Every rule file ends with the source behind each pattern it names, from Cockburn's hexagonal architecture to RFC 9457 and the OWASP cheat sheets. Kanōn's own stances are marked as such, so you know which is which.

  • 5

    editor dialects from one tree

    One source, five editors

    Write the standard once and generate it for Claude Code, Cursor, VS Code, Codex and Antigravity, plus a paste-in block for plain chat. A drift check in CI keeps the generated copies honest.

What ships

Five standard plugins, one opt-in airails pack for Java, one opt-in tools pack, one marketplace, plus three optional mods. A repo enables kanon-core plus its stack, and a monorepo enables all. Everything else in the tree is either enforcement (hooks, git hooks, CI scripts) or generated output.

Install per editor

Claude Code consumes the plugin package natively. Every other editor gets a generated dialect: run scripts/sync-editors.py against your repo. It needs only Python 3.

Native package

Claude Code

/plugin marketplace add themaverik/kanon
/plugin install kanon-core@kanon
/plugin install kanon-java@kanon        # per repo type: -java | -ts | -web | -rust
/plugin install kanon-tools@kanon       # optional: docker-dev, remove-ai-marks, diagram-on-the-fly

Per repo: sync the rules with sync-editors.py --tools claude (plugins can't ship them), copy templates/CLAUDE.md and templates/AGENTS.md to the root, fill placeholders, then commit this to .claude/settings.json so trusting the repo auto-installs:

{ "extraKnownMarketplaces": { "kanon": { "source": { "source": "github", "repo": "themaverik/kanon" } } },
  "enabledPlugins": { "kanon-core@kanon": true, "kanon-java@kanon": true } }

Teams can pin a semver tag and enforce the setup with managed settings. Finish with scripts/install-githooks.sh inside the repo.

Generated, two directory names

No editor at all

Plain chat: Claude, ChatGPT, Gemini

For copy-paste work in a bare chat interface, the standard compresses into one ~1.5K-char instruction block per stack. Paste it once into Claude Project instructions, ChatGPT Custom Instructions / a Project / a GPT, or a Gemini Gem. Then every snippet you request follows the same conventions as the full plugin. Keep exactly one option in the Architecture line and delete the other. Source files: templates/chat-instructions-backend.md · chat-instructions-frontend.md.

Backend: Java/Kotlin · Quarkus or Spring Boot 
You are a senior Java/Kotlin backend engineer. Follow these rules in every answer.

Discipline: surgical changes only. Touch what the task requires, match existing style, and list adjacent issues under "Noticed, not touched" instead of fixing them. Simplest code that works; no speculative abstractions. State assumptions before coding; if a premise in my request looks wrong, say so first. Flag any deviation from my request with its reason.

Java framework: [KEEP ONE] Quarkus | Spring Boot. Never mix them in one module.

Architecture: [KEEP ONE] Spec-Driven BCE, packages org.app.<bc>.<boundary|control|entity> | hexagonal: domain imports no framework code. Never mix the two.

Quarkus: CDI, no Spring annotations. @ApplicationScoped default, constructor injection, @ConfigProperty for config. Never block the event loop: blocking work behind @Blocking or @RunOnVirtualThread; reactive endpoints use reactive persistence. Prefer the platform over hand-rolled code: Dev Services, Panache, @Retry/@Timeout/@CircuitBreaker. Spring Boot: constructor injection and stereotypes, no field @Autowired; @ConfigurationProperties over @Value; @Transactional on services (self-invocation bypasses the proxy); errors as ProblemDetail via @RestControllerAdvice; SecurityFilterChain beans; open-in-view off; slice tests and Testcontainers @ServiceConnection. Kotlin: val by default, no !! outside tests, data classes, all-open handles CDI proxying, suspend endpoints over manual Mutiny chains. Target the Java/Kotlin version I state; immutability by default.

Testing: claims about failure modes need tests. Propose jqwik/kotest properties for invariants and PIT mutation score over coverage percent. Never delete or weaken a failing test; report it.

Output: code in fenced blocks. End nontrivial answers with four short sections: Deviations / Premises assumed / Noticed, not touched / How to verify. Commit messages: "KEY-123: imperative one-liner" plus up to 5 one-line bullets. No AI attribution footers anywhere.
TypeScript: NestJS · Next.js · general TS 
You are a senior TypeScript engineer (NestJS backend, Next.js frontend). Follow these rules in every answer.

Discipline: surgical changes only. Touch what the task requires, match existing style, and list adjacent issues under "Noticed, not touched" instead of fixing them. Simplest code that works; no speculative abstractions. State assumptions before coding; if a premise in my request looks wrong, say so first. Flag any deviation from my request with its reason.

TypeScript: strict mode. No `any` or non-null `!` on nullable paths without justification. Immutability by default. Every promise awaited or explicitly handled, error paths included; no floating promises.

NestJS: constructor DI, never `new` an injectable. Import other modules only via their exported surface; forwardRef needs written justification. Validate every inbound DTO at the controller edge (class-validator or zod). ORM entities never cross service boundaries; map to DTOs. Hexagonal repos: domain/use-case layers import zero @nestjs/* code.

Next.js/React: respect server/client component boundaries; no server-only imports in client bundles; fetch data in the right layer; accessibility and Core Web Vitals are requirements, not polish.

Testing: propose fast-check properties for invariants and Stryker mutation score over coverage percent. When a boundary violation repeats, propose the dependency-cruiser rule that freezes the fix. Never delete or weaken a failing test; report it.

Output: code in fenced blocks. End nontrivial answers with four short sections: Deviations / Premises assumed / Noticed, not touched / How to verify. Commit messages: "KEY-123: imperative one-liner" plus up to 5 one-line bullets. No AI attribution footers anywhere.

What deliberately does not compress into chat mode: hooks, git enforcement, Serena/graphify, and mutation runs. The snippet makes the model propose the right verifiers, but running them stays on your machine. The four-section answer footer (Deviations / Premises assumed / Noticed, not touched / How to verify) is the chat-sized version of the implementer's six-section handoff report.

All editors, always: run scripts/install-githooks.sh in the repo. The prepare-commit-msg git hook (ticket key from branch, pointwise skeleton) and CI verifiers are the enforcement layer every editor shares. Editor-specific hooks are Claude Code only. See Editor-Parity.md for exactly what does not port.

Set up a repo

Every repo starts with the same five steps. Then pick the recipe for your stack below.

Per-repo setup, always:
  1. Enable plugins in the repo's .claude/settings.json (snippet per stack recipe below).
  2. Copy templates/CLAUDE.md and templates/AGENTS.md to the repo root. Fill the three header lines: repo name, Stack, and Architecture (pick one option, delete the rest). That Architecture line is what activates BCE vs hexagonal rules. Nothing else needs editing.
  3. Run python3 scripts/sync-editors.py --repo . --stacks <list> --tools claude and commit .claude/rules/kanon/, .claude/kanon/ and .kanon/. Claude Code plugins can't ship rules, so this is how they reach the session. Re-run it after each Kanōn update.
  4. Run scripts/install-githooks.sh in the repo (ticket key + commit skeleton for every committer).
  5. Run graphify once at the repo root (tier-0 graph, which the graph-sync hook then maintains).
Non-Claude editors: replace steps 1 and 3 with python3 scripts/sync-editors.py --repo . --stacks <list> --tools <editor> and commit the generated directory.

Tech stack recipes

Each recipe fills in steps 1 and 2 for one stack: which plugins to enable and which lines to set in CLAUDE.md and AGENTS.md.

Java

Quarkus backend: Java, with BCE

  • Step 1 plugins: "kanon-core@kanon": true, "kanon-java@kanon": true, "kanon-java-airails@kanon": true
  • Step 2 Architecture line: keep Spec-Driven BCE in both files. That single line makes the bce skill govern packaging and suppresses hexagonal vocabulary.
  • Nothing else to configure: microprofile-server covers REST/config/fault-tolerance idioms (Quarkus implements MicroProfile), and rules/java/quarkus.md wins on Quarkus-specific conflicts automatically.
  • Optional adoption, per team decision: the sbce spec-driven workflow (one capability spec per business component) with ears-tests generating table-driven tests from the spec. Run them as /sbce and /ears-tests. They never activate on their own.
  • Recommended follow-up: ask Claude to "freeze our layering as Taikai/ArchUnit tests" once, so future violations fail the build instead of appearing in review comments.
Java

Quarkus backend: Java, without BCE (hexagonal or layered)

  • Identical to the above except Step 2: keep hexagonal (ports/adapters) or layered MVC in the Architecture line instead. The router then applies our ports/adapters layering rules and the BCE skill stays silent. The two are never mixed in one module.
  • Everything else is automatic: quarkus-reviewer on PRs and failure-mode-engineer with PIT + jqwik. With kanon-java-airails, java-conventions also applies at the repo's real Java version (it checks the toolchain first), and /continuous-testing runs the dev-mode loop.
Java · Kotlin

Spring Boot backend: Java or Kotlin

  • Step 1 plugins: the same as Quarkus: "kanon-core@kanon": true, "kanon-java@kanon": true
  • Step 2: set Java framework: Spring Boot in CLAUDE.md and AGENTS.md. Without it, java-discipline detects org.springframework.boot in the build file, and asks if it finds both frameworks or neither.
  • That loads rules/java/spring.md and routes review to spring-reviewer. The Quarkus-only skills, microprofile-server and continuous-testing, stay out.
Kotlin

Quarkus backend: Kotlin

  • Same plugins and steps as Java (the java plugin covers Kotlin). Step 2 Stack line: mention Kotlin, e.g. "Quarkus services (Kotlin)". rules/java/kotlin.md already self-activates on .kt files regardless.
  • One choice to make in the repo: detekt or ktlint-via-spotless as the lint baseline. Add whichever to the build, since the rules accept either but require one.
  • Everything else carries over unchanged. The ArchUnit/Taikai rules are the same (they run on Kotlin bytecode), all-open handles CDI proxying, and PIT runs with the Kotlin plugin, alongside kotest-property or jqwik. BCE vs hexagonal works exactly as for Java, because packages define layers, not the language.
TypeScript

NestJS backend (TypeScript)

  • Step 1 plugins: "kanon-core@kanon": true, "kanon-ts@kanon": true
  • Step 2: Stack line e.g. "NestJS APIs". Architecture line: hexagonal if your domain/use-case layers must stay framework-free (the boundary reviewer's first check), otherwise layered MVC.
  • One-time in the repo: add .dependency-cruiser.js and knip config if absent. Ask Claude to "add dependency-cruiser boundary rules for our module layout", and the nestjs-boundary-reviewer quotes their output instead of opining.
TypeScript · Web

Next.js frontend

  • Step 1 plugins: core + -ts + -web (all three).
  • Step 2: Stack line e.g. "Next.js portal". Architecture line: layered MVC is usually right for frontends, so delete BCE/hexagonal.
  • The web rules (design quality, performance, patterns, security, testing with accessibility checks, plus frontend.md for server/client component boundaries) are loaded by the frontend-discipline router when you work on .tsx. Add Playwright as the e2e layer (see Companion tools).
TypeScript

Other TypeScript projects (libraries, CLIs, workers)

  • Step 1 plugins: core + -ts only.
  • No extra configuration: the NestJS rule file self-scopes (it applies only when @nestjs/* is in package.json), so plain TS repos get strictness, knip, Stryker, fast-check, and commit discipline with nothing to turn off.
Rust

Rust crates and axum services

  • Step 1 plugins: "kanon-core@kanon": true, "kanon-rust@kanon": true
  • Step 2: Stack line e.g. "axum API, Rust workspace". Architecture line: hexagonal fits Rust well. The domain crate defines the port traits and depends on no framework or I/O crate, adapters implement them, and the binary crate wires them together.
  • One-time in the repo: add a deny.toml if absent, so the rust-reviewer runs cargo deny check for advisories, licenses and duplicate versions. It also runs clippy with -D warnings and rustfmt.
  • The axum rule applies only when the crate depends on axum, so libraries and CLIs get the Rust rules alone. Tests use cargo-nextest, proptest and insta, and cargo-mutants supplies the mutation evidence.

If you forked with your own plugin prefix, substitute it for kanon above. For docs-only or mixed repos, enable core alone and everything stack-specific stays out of context.

Execution workflow

Every Standard/Milestone task runs this track. Trivial work forks off after the premise check and skips dispatch entirely. Source lives at docs/workflow.mmd.

  • Ticket + brief: no Standard work without a key. The brief carries success criteria and pasted ticket context.
  • Tiered read: graph (graphify) for structure, Serena for symbols, and targeted lines before any behavioral claim. Full files only when editing.
  • Premise check: cheap falsifiable checks in main context (~2K tokens) catch the premise-level failures that 160K of agent work will not.
  • Budget gate: every dispatch is classed by expected peak context, S (<60K) / M (60–150K) / L (>150K), measured against real subagent peaks (median ~105K). Approval follows the plan: M and L on Pro, L on Max, Team and API. Escalating above the plan's agent model (Sonnet by default) always needs approval, and Fable is capped per session (Pro 0, Max 5x 1, Max 20x 2). cache-keeper's cost mode can enforce the model rules.
  • Implementer: fresh context, env-mutation and cooldown guards, ~15-file stop rule, and the mandatory six-section handoff report (what changed, deviations from the brief, premises verified or corrected, noticed but not touched, commands run, how to verify).
  • Verify: PIT/Stryker mutants and jqwik/kotest/fast-check properties are the evidence. Coverage percent is not.
  • Review: pr-reviewer on every PR, architect-review plus the stack reviewer (quarkus / spring / nestjs-boundary), all read-only. Design changes are recorded as ticket-linked ADRs.
  • Commit & deliver: commit-craft message (KEY: one-liner + bullets, no AI footers), ticket-guard backstop, remove-ai-marks (kanon-tools) on published artifacts.

Mods: session tools above the prompt

Three optional plugins that draw a band above the Claude Code prompt. Each one works in any repo and doesn't need the others. They use Claude Code's hooks modules, so they need a build that supports them.

/plugin install cache-keeper@kanon

cache-keeper

Keeps cost and cache in view, and decides when to compact from what the last turn did.

  • Line one, left to right: time before the prompt cache expires, context size, 5-hour and weekly rate-limit use, this session's cost, and what the next message costs if the cache goes cold.
  • Handoff & Clear (h) or /handoff: writes a handoff brief, clears the session and puts the brief in the prompt to review and send. Fresh (f) clears without a brief.
  • /autohandoff 80k hands off at that context size, and /autohandoff off stops it. /cache-ttl <minutes|auto> sets the cache TTL by hand. By default it is detected.
  • Cost mode is line two: the profile for your plan (read from your account, or set profile to pro, max5, max20, team or api), main model and effort, agent defaults, Fable use, and the compaction target and ceiling. It only displays by default. Turn on enforce to rewrite agent model and effort, cap Fable per session, stop auto-compaction below the target, and get asked to compact when it is due. Add autoCompact to compact between turns without asking.

Adaptive compaction. The target is your measured floor plus room, and the ceiling adds a grace buffer, both held under a per-plan cap. Between them, a heavy turn compacts, because work in flight keeps growing. A short query holds inside the grace instead. At the ceiling it compacts regardless. The ctx reading turns orange past the target and red past the ceiling. Grace keeps the plans' ratio, Pro 1 : Max 5x 3 : Max 20x 8.

Why: recall drops as context grows on every model these studies tested (Chroma, Context Rot; UIUC, arXiv 2510.05381). prompt-enhancer

Prompt [ Enhance ] [ Undo ]

Type a draft, then press Enhance (e) or run /enhance. A small model rewrites it and wraps it in your template. Nothing is sent: you edit and press Enter. Undo (u) restores your draft until you send.

Templates are Markdown files in ~/.claude/prompt-templates/. {{task}} takes the rewritten prompt, {{implementer}} the implementer, and {{reviewer}} the reviewer picked for the area. /enhance <name> picks one, and /templates lists them.

Settings for each mod are under /plugin: cache-keeper ttlMinutes, warnTokens, inputUsdPerMtok, enforce, autoCompact, compactRoomTokens, compactGraceTokens, compactCapTokens. collision-guard has windowMinutes, and prompt-enhancer has model plus one agent name per role. The defaults are staff-engineer, backend-architect, frontend-developer, security-auditor and code-reviewer.

Memory management

Claude Code: use the native memory, correctly

  • Auto Memory maintains its own MEMORY.md outside the repo. Leave it on and never commit it. It carries session continuity, and you do nothing.
  • CLAUDE.md hierarchy is deliberate memory: repo root for the standard (from the template), ~/.claude/CLAUDE.md for personal preferences only, never org policy. Levels are additive.
  • Quick capture: start a message with # to file a note into memory, or /memory to inspect and edit what's stored.
  • ADRs are the durable, shareable memory: decisions go to docs/adr/ via adr-manager, ticket-linked. That is the memory other people and other editors can read.

Other editors, and the one rule that holds everywhere

  • Cursor: built-in Memories (Settings → Rules & Memories) cover session continuity per project.
  • Antigravity: its knowledge/memory lives under ~/.gemini, and workspace rules carry the standing context.
  • VS Code / Codex: no rich native memory. AGENTS.md + ADRs + the ticket carry context between sessions, so paste relevant ticket context into briefs.
  • External managers (mem0 MCP and similar) only if you need one memory shared across editors. It costs an extra MCP schema per session and most teams do not need it. Check the licence (some are AGPL) before using one in an enterprise.
  • The invariant, enforced by the artifact-guard hook: committed docs describe the system (ADRs, diagrams, runbooks), and nothing committed describes the session. That means no MEMORY.md, SESSION/PROGRESS notes, or generated knowledge bases in any repo.

Session continuity: across sessions, without committing session files

Cross-session state has exactly three sanctioned homes. The artifact-guard hook blocks the unsanctioned fourth (session files in the tree):

  • Tool-native memory (machine-local): Claude Code Auto Memory plus claude --resume/--continue restore prior sessions from ~/.claude, outside the repo. Cursor Memories and Antigravity's ~/.gemini store fill the same role there.
  • The ticket (team-shared, cross-editor): status, open questions and next steps. When an agent handoff report must outlive the session, paste it into the ticket or PR description and never commit it as a file. Resuming = re-read the ticket + the last handoff report there. This is the layer that follows you to a second machine or a second editor. Machine-local memory does not.
  • The repo (system-level only): ADRs, diagrams, runbooks: durable decisions, never session state.

Efficiency: how this compares

The design rests on a few widely discussed observations: command-line tools are usually cheaper in tokens than MCP servers for equivalent tasks, large MCP servers can add tens of thousands of tokens of tool schema before any work starts, and huge skill or agent libraries tax every session through their registries. The kanon figures below are estimated from this repo's files. The comparison rows are community-reported ballparks without a primary source, so read them as directional only.

Where the usage actually goes is dispatches, not registries. In the author's own transcripts subagents took 22–43% of all tokens. That is why the plan-aware S/M/L gate, diff-first reading, the ~15-file agent stop rule, handoff reports instead of transcript resumption, and sonnet-by-default (opus by approval) are part of the standard itself rather than advice.

Install and fork

Install

The repository is the marketplace (.claude-plugin/marketplace.json at the root). In Claude Code:

/plugin marketplace add themaverik/kanon

Then install the plugins you need, as shown under Install per editor. Per consuming repo the checklist is three steps: enable plugins (or run sync-editors.py), copy and fill the two templates, run install-githooks.sh.

Fork and customise

  • Fork the repo and edit rules, skills and agents under plugins/. Re-run scripts/sync-editors.py against your repos to pick up the changes.
  • Optional: if you want your own plugin prefix, run python3 scripts/rename.py --prefix <your-prefix> --org "<Your Org>" --dry-run first, then without --dry-run. Skip it if the kanon names suit you.
  • For forks, run scripts/leak-check.sh in CI. It scans the tree for terms you do not want published. Set the BANNED environment variable (a regex such as acme-internal|project-x) to add your own.
  • Version with semver tags so consumers can pin. The vendored airails skills come from upstream (MIT), and attribution is in plugins/kanon-java-airails/skills/Airails-Notice.md.
